# Security Verification Checklist — Real GAS Staging

Manual checklist for a human operator, to run against the staging
project from `STAGING_SETUP_CHECKLIST.md`. Nothing here is automated —
some items require the Apps Script editor UI directly (Script
Properties, execution identity), which this repository's tooling has no
way to reach.

**No secret, PIN, or credential should ever be pasted into a file that
gets committed to this repository — including this one.** Where a check
below asks you to look at a value, record only PASS/FAIL/the fact that
it was checked, not the value itself.

## Script Properties

- [ ] Open the staging project → Project Settings → Script Properties.
  Confirm `HMAC_SECRET` exists (it is auto-generated by `getSecret_()`
  the first time any token-issuing code path runs — logging in once is
  enough to trigger it if `setupSpreadsheet()` didn't already).
- [ ] Confirm `SS_ID` exists and its value is the staging spreadsheet's
  own ID (not the real production spreadsheet's ID — a mismatch here
  would mean the script is silently pointed at the wrong sheet).
- [ ] **`HMAC_SECRET` is not returned by any API.** Call `login` via
  `staging-smoke-test.js` (item 1) and inspect the raw response — confirm
  it contains only `{ok, token, ...}`, never the secret string. (Already
  verified structurally true of the code itself in
  `backend/production/PRODUCTION_READINESS_AUDIT.md` Part C — this step
  confirms it holds for the real deployed instance too.)

## `Config!LOGIN_PIN`

- [ ] Open the `Config` sheet, find the `LOGIN_PIN` row.
- [ ] If its value is `psp2026` (the legacy default seeded by
      `backend/legacy/Code.gs`), record:

  > **LEGACY DEFAULT ACTIVE — ROTATION REQUIRED**

  Do not change it as part of this checklist unless you are
  deliberately testing rotation. Do not write the value (default or
  rotated) into any committed file, including this one.

## Authentication chain (via `staging-smoke-test.js` and manual spot checks)

- [ ] `login` with a real Team name + correct PIN succeeds (item 1).
- [ ] `login` with a wrong PIN fails with a generic message, not a stack
      trace (item 2).
- [ ] **Brute-force lock**: attempt 5 wrong-PIN logins for one Team name
      in a row, then attempt the correct PIN — confirm it is also
      rejected (locked), matching `backend/production/Code.gs`'s
      `LOGIN_MAX_FAIL`/`LOGIN_LOCK_SEC` constants. Wait out the lock
      window (15 minutes) or use a different Team name to continue
      testing.
- [ ] **Rate limiting**: fire ~65 authenticated requests within a minute
      as one user; confirm requests beyond the 60th return the
      "Terlalu banyak permintaan" message, and a second user is
      unaffected. (`concurrency-test.js`'s Scenario A, run with
      `STAGING_CONCURRENCY=65`, doubles as a rough check of this, though
      it isn't its primary purpose.)
- [ ] `bootstrap` (or any protected action) without a token returns
      `authError:true` (item 3).
- [ ] `bootstrap` with a garbage/malformed token returns `authError:true`
      (item 24).
- [ ] **Expired token rejection**: this cannot be produced by a normal
      login (tokens are valid for 8 hours). To test it for real, either
      wait 8+ hours and reuse a captured token, or — if you have Apps
      Script editor access — temporarily run a one-off test function in
      the staging project that calls `verifyToken_` with a manually
      forged, already-expired payload signed via the project's own
      `signPayload_`, exactly as this repository's mock tests do
      (`backend/production/test/production-readiness-test.js`, Category
      2) — but run *inside* the real Apps Script editor this time, so it
      uses the real HMAC secret and real `Date.now()`.
- [ ] **Forged token rejection**: take a real, valid token from step 1,
      change one character in its payload segment (before the `.`), and
      confirm the tampered token is rejected (signature no longer
      matches).

## Sanitization

- [ ] `staging-smoke-test.js` item 25 (formula-injection safety, opt-in
      via `STAGING_ALLOW_WRITE_TESTS=true`) confirms `sanitizeStr_` is
      active on the real deployment for `addProjectMaster`. Delete the
      probe row it creates afterward.
- [ ] **Unauthorized write requests fail safely**: attempt a write action
      (e.g. `createWBS`) with no token, and again with an invalid token —
      confirm both are rejected with `authError:true` and no row is
      created (spot-check the sheet, or re-run
      `staging-smoke-test.js`/`concurrency-test.js` before and after and
      diff the row counts).

## Web App configuration

- [ ] **Execution identity**: Deploy → Manage deployments → confirm
      "Execute as" matches `backend/staging/appsscript.json`'s
      `webapp.executeAs` (`USER_DEPLOYING`).
- [ ] **Access settings**: confirm "Who has access" matches
      `webapp.access` (`ANYONE_ANONYMOUS`) — this is intentional (the
      frontend has no Google-account login step; the app's own HMAC
      token system is the real auth boundary), not an oversight. If this
      value is anything else, `staging-smoke-test.js` will likely fail
      at every item with an authorization/redirect error rather than a
      normal JSON response — that is itself a useful diagnostic signal.
- [ ] **Spreadsheet permissions**: confirm the staging spreadsheet is
      shared appropriately for the deploying account to read/write it,
      and that no broader sharing was accidentally left on (e.g., "Anyone
      with the link can edit" on the spreadsheet itself, which would be a
      real, separate exposure from the Web App's own access setting).

## Summary of what this checklist can and cannot conclude

Every item above that references `staging-smoke-test.js`/`concurrency-test.js`
is objective and repeatable. The Script Properties, execution identity,
and spreadsheet-permissions items require the Apps Script/Sheets UI
directly and are inherently manual — no script in this repository can
observe them from outside. Do not mark this checklist complete until
every box is checked by an actual human looking at the actual staging
project.
